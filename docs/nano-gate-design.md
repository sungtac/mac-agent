# 나노단위 z코딩 게이트 설계 — 통합검사는 위험도 기반 선택 실행

**상태: 설계 확정, 미구현.** 이 문서는 코드가 아니라 결정 기록이다. 2026-07-30, `verify-task-stop-check.sh`가 작은 버그 수정 하나에도 v1(무조건 풀-웨이트, 코덱스+안티그래비티 반복 채점)을 안내해서 30분/65만+ 토큰이 든 사고가 있었고, 콕스가 이를 v2(경량/전체 티어 자동 분기) 안내로 고쳤다. 사용자가 이 교훈을 "토큰 사용량 균형화" 전체 운영 원칙으로 확장하자고 제안했고, 맥·콕스가 Discord에서 3라운드 상호 비평(제안→재의견→재재의견)을 거쳐 수렴한 결과가 아래다. 구현 전 이 문서를 먼저 읽을 것.

## 배경 — 사용자 원 제안

기존 논의(v1→v2 교훈)를 "작업 규모에 맞춰 검증 강도를 자동 조절한다"는 단순 최적화에서 그치지 않고, Claude/Codex 양쪽의 토큰 사용량 균형화 + 실행 방식 자체(나노단위 z코딩)로 확장하자는 것이 출발점이었다. 사용자의 구체적 질문: "최종 리뷰가 꼭 필요한가? 오히려 톱니바퀴처럼 안 맞물리는 모든 오류를 색출하고, 관련 정보를 빠짐없이 수집해서 개선계획을 나노단위로 쪼갠 뒤, 각 나노단위가 끝날 때마다 코드품질+톱니바퀴 검증을 하고 이상 없을 때만 다음 단계로 넘어가는 방식(z코딩)이 낫지 않은가?"

## 핵심 결론 — 최종 리뷰는 없애지 않는다, 선택 실행으로 바꾼다

나노단위 로컬 게이트와 최종/통합 리뷰는 대체 관계가 아니라 서로 다른 오류를 잡는 보완 관계다.

- **나노 게이트(로컬)**: "이 스텝이 자기 할 일을 제대로 했나"에 강하다. 근시안적이라, 아직 안 온 스텝이 지금 스텝의 암묵적 가정에 기대는 경우를 못 잡는다.
- **통합 검사(전역)**: 개별로는 통과했는데 누적되며 생기는 불일치("톱니바퀴 안 맞물림" 그 자체)를 잡는다. 나노단위로 잘게 쪼갤수록 전체 그림을 보는 시야는 더 파편화되므로, 쪼갤수록 이 체크가 덜 필요해지는 게 아니라 더 필요해진다.

따라서 **나노 게이트는 상시·가볍게, 통합 검사는 위험도·누적 변경량 기준으로 선택 실행**하는 구조로 확정한다. 매 나노 스텝에 풀 리뷰를 붙이는 것도, 통합 검사를 아예 없애는 것도 둘 다 기각.

## 전체 흐름

```
계획
  ↓
계약 단위 수정 (나노 스텝 1개)
  ↓
자동 기록 (오케스트레이터가 구조화된 이벤트로, 기록 실패 시 다음 단계 진행 차단)
  ↓
light 검증 (diff 기반 가벼운 품질 체크)
  ↓
누적 위험도 재평가 (공통 위험도 함수, 순수 계산)
  ↓
[임계치 초과] → 통합 검증 (여러 모듈 연결 시 중간 통합 / 인증·라우팅·사용량·배포급 변경 시 최종 리뷰 필수)
  ↓
[임계치 이내] → 다음 나노 스텝으로
```

## 결정 1 — 나노 단위 = "계약 단위" (조작적 정의 포함)

"파일 1개" 또는 "함수 1개" 같은 개수 기준은 기각. 어떤 함수는 관련 모듈 여러 개를 동시에 바꿔야 하고, 어떤 파일은 너무 커서 한 단계로 부적절할 수 있다. 대신 **"독립적으로 검증·롤백 가능한 계약 단위"**로 정의하되, 이 자체가 또 모호해지지 않도록 조작적 정의를 하나 더 못박는다:

> 나노 스텝의 경계 = **그 지점까지의 diff가 기존 린트/타입체크/테스트를 깨지 않고, 그 자체로 되돌릴 수 있는 지점.**

이러면 "계약 단위인가 아닌가"를 사람 판단이 아니라 기존 검사 도구 통과 여부로 기계적으로 확인할 수 있다.

## 결정 2 — 공통 위험도 판정 함수 (순수 함수, LLM 호출 금지)

기존 `verify-task-v2.js`의 `decideTier()`(파일수≤3 AND 민감경로 미포함 → light)를 그대로 복사하지 않고, 다음 입력을 받는 공통 함수로 승격한다:

- 이번 나노 스텝의 변경 파일 수
- **누적** 변경 파일 수 (마지막 통합 검사 이후 누적)
- 민감 경로 포함 여부 (설정/보안/`.github/workflows`/공개문서 등, 기존 목록 재사용)
- 의존성 경계 — 정적 신호(import 그래프, 파일 경로 패턴)로만 계산 가능한 선까지만. **이 함수 자체는 반드시 순수 함수로 남아야 한다** — "의존성 경계"를 판단하려고 여기에 에이전트 호출을 끼워 넣으면 판정 자체가 무거워져서, 없애려던 오버헤드가 판정 단계로 옮겨붙을 뿐이다.
- 잔여 토큰(양쪽 provider의 `coach` 사용량 창)

출력: light(나노 게이트만) / mid(중간 통합 검사) / full(최종 리뷰 필수 — 인증·라우팅·사용량·배포급 변경).

## 결정 3 — 성공/실패 기록은 자동 이벤트, 사람이 안 씀

산문 보고서가 아니라 나노 스텝이 통과할 때 오케스트레이터가 자동으로 구조화된 이벤트를 남긴다. **기록 자체가 게이트 조건**이다 — 기록 실패 시 다음 단계로 못 넘어간다. 산문 보고서는 선택 사항으로만 둔다. (이유: 로깅이 "권장"이면 바쁠 때 생략되고, 그러면 하네스가 실제로 안 쌓인다.)

최소 기록 필드:
- 작업 유형과 변경 파일
- 사용한 에이전트
- 소요 시간과 토큰
- 검증 티어 (light/mid/full)
- 성공·실패 원인
- 재발 방지 규칙

**멱등 키 필수 (`task_id` + `step_id`).** 기록 실패 시 재시도하거나 프로세스가 죽었다 재시작하면 같은 나노 스텝이 두 번 기록될 수 있다 — 이러면 하네스가 오염되고, 오염된 하네스로 다음 위험도 판정을 하게 되어 설계 전체의 신뢰도가 흔들린다. 이벤트 기록은 `task_id+step_id` 조합으로 멱등해야 하며, 같은 키로 재기록 시 덮어쓰기(또는 무시)만 허용하고 append 중복은 금지.

**성공 사례도 반드시 기록한다.** 실패만 쌓이면 회피 규칙만 늘어나 점점 보수적으로만 수렴해(결국 뭘 시켜도 무겁게 검증) — "이 규모는 light로도 충분히 통과했다"는 성공 기록이 있어야 과잉검증을 막는 반대 압력이 생긴다.

## 하네스와의 관계

기존 `docs/codex-harness.md`(append-only, 코덱스 전용 규칙 누적)를 재사용하되, 이번 논의로 확장되는 지점:
- 코덱스뿐 아니라 맥·콕스 양쪽의 라우팅 판단(누가 맡았을 때 성공/실패했는지, 시간/토큰)까지 구조화 기록 대상에 포함.
- append-only로 계속 쌓이기만 하면 나중에 파일이 커져 매번 읽는 비용이 커지거나 모순 규칙이 섞일 수 있다 — 당장은 아니고, 실측하며 필요해지면 트렁케이션/요약을 정할 것 (기존 문서에도 이미 미정 항목으로 남아 있음, 그대로 승계).

## 아직 안 정해진 것 (구현 시 확정)

- 위험도 함수의 정확한 임계값 수치 (파일수 몇 개부터 mid, 몇 개부터 full / 잔여 토큰 몇 %부터 경보).
- 의존성 경계를 정적으로 계산하는 구체 알고리즘 (import 그래프 파싱 범위, 언어별 처리).
- 나노 게이트 실행 루프를 `verify-task-v2.js`에 통합할지, 별도 워크플로우로 둘지.
- 하네스 파일 무한 증가 문제 (기존 미정 항목 승계).

## 구현 계획 (초안, 단계별)

0. **기존 구조·호환성 기준선 확인 (읽기 전용)**: 구현 시작 전에 아래를 먼저 확인 — `verify-task-v2`가 현재 받는 입력/반환값, 기존 하네스(`docs/codex-harness.md`) 기록 형식, Stop hook(`verify-task-stop-check.sh`)이 검증 결과를 판정하는 방식, 이벤트를 저장할 위치와 동시 기록(concurrent write) 가능 여부, 기존 작업 흐름을 깨지 않는 호환성 조건. 저비용 사전점검이라 생략할 이유가 없음 — 이걸 건너뛰면 나노 게이트가 기존 계약과 충돌하는 걸 구현 다 하고 나서야 발견하게 된다.
1. **위험도 함수**: `workflows/lib/`에 `decide-risk-tier.js`(가칭) — 기존 `decideTier()`를 흡수해 위 5개 입력을 받는 순수 함수로 재작성. 유닛 테스트로 임계값 케이스 검증.
2. **버전이 있는 나노 이벤트 스키마 + 원자적 자동 기록**: 나노 스텝 통과 시 남길 JSON 이벤트 스키마 정의(스키마 버전 필드 포함), `task_id+step_id` 멱등 키로 원자적 기록, 기록 실패 시 진행 차단 로직 구현 (기존 `codex-harness.md` append 로직 패턴 재사용).
3. **나노 게이트 루프**: 계획 → 계약단위 수정 → 자동기록 → light검증 → 위험도 재평가 → (필요시) 통합검증 흐름을 실제 워크플로우 스크립트로 구현, 기록 실패 시 중단하는 게이트 포함 — `verify-task-v2.js` 확장 vs 신규 워크플로우 여부는 1~2단계 구현하며 결정.
4. **파일럿 실행**: 저위험 작업 + 경계 사례(임계값에 걸치는 케이스) 각 1건을 이 흐름으로 돌려서 이벤트 기록·위험도 재평가·통합검사 트리거·복구(재시도/재시작 시 멱등성)가 의도대로 동작하는지 확인.
5. **임계값 조정**: 파일럿에서 나온 실제 시간·토큰·실패율을 바탕으로 위험도 함수의 임계값을 확정.
6. **문서화**: 파일럿 검증 끝나면 이 문서 상태를 "구현됨"으로 갱신하고 `CLAUDE.md` 인덱스에 항목 추가 (기존 `verify-task-v2` 항목 옆).

처음부터 전체 작업에 적용하지 않고, 작은 파일럿 하나로 기록·게이트·복구 흐름부터 검증한 뒤 확장한다.
