# token-cost-report.sh (토큰비용 대시보드 일일 크론)

상태 메모: Discord 알림 경로는 2026-08-02 퇴역했다. `discord-notify.sh`는
호환성 shim으로 남아 있지만 외부 전송은 수행하지 않는다. 토큰 비용 리포트 자체와
로컬/Drive 저장 경로는 계속 활성이다.

`cron/token-cost-report.sh` — 매일 23:00 `launchd`
(`~/Library/LaunchAgents/com.macagent.token-cost-report.plist`, 레이블
`com.macagent.token-cost-report`, `Hour: 23, Minute: 0`, `Weekday` 키 없음=매일)로 실행.
Drive 설치형 포터블 스킬 `token-cost-dashboard`의 `analyze_sessions.py`를 저장소별로 돌려서
Drive `토큰비용리포트/YYYY-MM-DD/<repo>.html`에 저장한다.

## 배경 — 왜 24시간인가 (2026-07-29 정정)

실밸개발자 Claude Code 강의 2편 리뷰 후 만든 두 스킬(`ai-readiness-cartography`,
`token-cost-dashboard`) 중 이것만 크론 연동했다. 사용자가 "24시간이면 어떨까"라고
물어봐서(2026-07-29) 판단 근거를 정리했었는데, 그중 세션 볼륨 근거는 사후 재검증
(N6, 2026-07-29)에서 박약한 것으로 드러나 정정한다:
- `analyze_sessions.py`는 기존 Claude Code 세션 로그를 파싱만 하는 순수 스크립트라 실행
  비용이 싸다 — `claude -p` 호출이 없어서 `weekly-report.sh`/`kakao-morning-briefing.sh`를
  괴롭히는 간헐적 헤드리스 행(hang) 이슈도 원천적으로 해당 없음. **이 근거는 유효.**
- ~~실측(2026-07-29)해보니 mac-agent 하루 세션 수가 여러 건이라 일일 추세를 보는 게
  말이 됨~~ — **정정**: 재조사해보니 그 실측은 딱 4일치 기록(07-25: 16건, 07-26: 25건,
  07-27: 10건, 07-29: 1건, 진행중)뿐이었고, 그 4일 자체가 이번 개선 작업으로 세션이
  몰린 특이 구간이었다. "평소에도 세션이 많다"는 안정적 베이스라인이 아니라 이 작업
  기간의 일시적 스파이크를 근거로 삼은 것 — 판단이 틀렸다기보다 근거가 얇았다는 뜻.
  데이터가 더 쌓이면(평시 몇 주치) 재판단할 것. 다만 위 첫 근거(실행 비용이 싸서
  자주 돌려도 부담 없음)만으로도 24시간 주기 자체는 여전히 무난한 선택.
- 반면 `ai-readiness-cartography`는 매번 Claude가 저장소를 실제로 읽고 판단해야 해서
  실행 자체가 비싸고, 코드베이스 구조는 하루 만에 잘 안 바뀌어서 24시간 주기는 과함 —
  그래서 **크론 연동 안 함**(수동 실행 유지). 나중에 필요해지면 별도 판단.

## exit code 구분 (2026-07-29, 이 크론 만들면서 `analyze_sessions.py`에 추가한 것)

`analyze_sessions.py`가 원래는 "세션 없음"과 "진짜 크래시"를 둘 다 그냥 실패로 뭉뚱그렸다 —
크론이 여러 저장소를 매일 도는데, 아직 그 저장소로 Claude Code 세션을 한 번도 안 켠 날이면
매번 "실패" 알림이 뜨는 스팸이 될 뻔했다. 그래서 exit code를 나눴다:
- `0` — 성공, 리포트 생성됨.
- `2` — 세션 로그 없음(그 저장소를 그날/그때까지 안 썼다는 뜻, 정상 상태) — 조용히 스킵,
  디스코드 알림 안 보냄.
- 그 외(1, 또는 처리 안 된 예외로 인한 트레이스백) — 진짜 실패, 디스코드로 알림.

`ANALYZE_SCRIPT` 자체가 없을 때의 함정(2026-07-29 N5 실측 발견·수정): `python3
<존재하지 않는 파일>`은 파이썬 인터프리터 자체가 "파일 없음" 오류로 exit code **2**를
반환한다 — 이게 `analyze_sessions.py`의 "세션 없음(정상)" exit code 2와 정확히 겹친다.
고치기 전엔 스크립트 배포가 잘못되거나 skill-catalog 재설치가 실패해도 크론이 "오늘은
세션이 없나보다"로 조용히 넘어가서 디스코드 알림이 영영 안 오는 함정이었다. 그래서 루프
진입 전에 `[ -f "$ANALYZE_SCRIPT" ]`를 먼저 확인해 없으면 즉시 별도 알림 후 exit 1로
끝나도록 고쳤다(실제 Discord 왕복으로 검증 완료 — 알림이 실제로 도착하는지 메시지 ID로
재조회까지 확인).

## launchd 수면-지연 특성 (2026-07-29 N6, 실측 근거로 문서화)

`launchd`의 `StartCalendarInterval`은 맥이 그 시각에 잠들어 있으면 정시에 못 돌고, 깨어난
직후에야 뒤늦게 실행된다 — 이 크론 자체의 로그 이력은 아직 짧아 직접 증거가 부족하지만,
같은 방식(`StartCalendarInterval`, 매일)을 쓰는 `kakao-morning-briefing`(일일 09:00)의
실행 이력 2건을 대신 근거로 삼는다: 하나는 정시(+18초), 하나는 9시간 38분 늦게 실행됨(맥이
자고 있다가 깨어난 뒤 launchd가 뒤늦게 발화한 것으로 추정 — 표본이 2건뿐이라 확정은 아니고
정황 증거). `weekly-report`는 캡처된 로그가 전부 수동 테스트 흔적(목요일이 아닌 날짜)이라
자동 발화 타이밍에 대한 증거가 아예 없다.

이 크론(`token-cost-report.sh`)에는 이 특성이 **문제가 아니다** — 저비용 트렌드 리포트라
그날 하루 안에만(또는 늦게라도) 한 번 돌면 기능적으로 충분하고, 정시성이 중요한 알림성
작업(예: 아침 브리핑)과 달리 지연 자체를 감내할 수 있는 종류의 작업이기 때문. 그래서
watchdog/재시도 로직을 별도로 추가하지 않는다 — 위 "배경" 섹션의 첫 번째 근거(실행 비용이
싸서 자주 돌려도 부담 없음)와 같은 맥락으로, 이 크론의 저비용/저위험 특성이 여러 설계
판단(주기·재시도 생략·지연 감내)을 관통한다.

## 알려진 제약

- 리포트가 매일 쌓인다(`토큰비용리포트/YYYY-MM-DD/`) — 오래되면 Drive 용량을 차지하니
  필요하면 나중에 보존 기간 정책을 따로 정할 것(아직 자동 정리 없음).
- `discord-notify.sh`는 실패 시 일방향 알림만 — Phase 2 v1 스타일 답장 재시도는 이 크론엔
  아직 없음(가치 대비 우선순위 낮다고 판단, 필요해지면 추가).
