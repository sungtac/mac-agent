# verify-task v2 — 3자 품질 게이트 설계 (확정, 미구현)

**상태: 설계 확정, 구현 전.** 이 문서는 코드가 아니라 결정 기록이다. 2026-07-25~26에 걸쳐 사용자·Claude·Codex·Antigravity·Plan 에이전트가 여러 라운드로 검토하며 나온 최종 설계이고, 결정마다 "왜"를 남긴 이유는 — 한 번 순서 오류(안티그래비티가 경량 트랙에도 다시 끼어드는 실수)가 실제로 났었고, 글로 확정 안 해두면 다음에 또 어긋나기 때문이다. 구현 시 이 문서를 먼저 읽고, 여기 없는 임의 변경은 하지 말 것.

## 목적

기존 `verify-task.js`는 완료된 작업을 Codex+Antigravity 양쪽에 사후 채점만 시킨다(고정 rubric, 85점 통과). v2는 여기에 **작업 시작 전 스펙 고정 + 시작 전 초안 경쟁**을 더해서, "다 하고 나서 채점"이 아니라 "시작 전에 기준을 못박고, 그 기준으로 검증"하는 구조로 확장한다. 1차안(모든 지시에 5단계 왕복, 즉흥 채점표, 90점 단일기준)은 Codex/Antigravity/Claude 3자에게 전부 과잉설계로 지적받고 폐기됐고, 아래는 그 지적들을 반영해 여러 라운드 개정을 거친 최종안이다.

## 적용 범위

일반 대화형 질문·답변은 제외. `.md` 문서 작업, 코드레벨 작업, "파일 정리해줘" 같은 개별 지시까지 포함해 "작업"이라 부를 만한 것 전부.

## 호출 방식: 수동, 훅 아님

Codex·Antigravity·Plan 3자 만장일치 결론. Claude Code의 `UserPromptSubmit` 훅이 실제로 존재하고 프롬프트 처리 전에 개입 가능하다는 것까지 확인했지만(기본 timeout 30초, 연장 가능), 전체 트랙은 최악의 경우 외부 CLI 호출 7~9회로 5~15분이 걸릴 수 있어 사용자를 동기적으로 막는 훅과 구조적으로 안 맞는다. 기존 `verify-task`처럼 **명시적으로 호출하는 워크플로우**로 남긴다.

## 전체 흐름

```
컨텍스트수집(클로드, 기계적)
    ↓
티어판정(기계적 규칙: diff 파일수 ≤3 AND 민감경로 미포함 → 경량 / 그 외 → 전체)
    ↓
┌─ 경량 ────────────────────────────┐   ┌─ 전체 ──────────────────────────────────┐
│ 클로드 실행                        │   │ 안티: 스펙 + 고정60~70% + 동적30~40%     │
│   ↓                                │   │ 채점표 작성                              │
│ 코덱스 평가                        │   │   ↓                                     │
│ (완료조건 스스로 먼저 명시 후 채점, │   │ 코덱스 1회 반박권                        │
│  탈출구 보유 — 아래 참고)          │   │   ↓                                     │
│ → 안티 호출 0회                    │   │ 초안경쟁(코덱스+안티, 서로 결과 안 봄)    │
│                                     │   │   ↓                                     │
│                                     │   │ 클로드 종합(짧은 지시문만)                │
│                                     │   │   ↓                                     │
│                                     │   │ 코덱스 실행                              │
│                                     │   │   ↓                                     │
│                                     │   │ 안티 평가(거부권 보유)                    │
└─────────────────────────────────────┘   └──────────────────────────────────────────┘
    ↓
클로드 최종판정 (거부권 확인 → 점수 확인 → 승인/재시도, 노이즈 표시 포함)
    ↓ (재시도 2회 초과 시)
사용자 에스컬레이션
```

## 컨텍스트 수집 (첫 단계, 클로드, 기계적)

`git status` / `git diff --stat` / 변경 파일 목록 + **관련 컨벤션 문서(CLAUDE.md 등)** + **테스트 실행 명령**까지 포함. 이게 없으면 뒤에서 안티가 "기존 컨벤션 준수" 항목 자체를 판단할 근거가 없다. 안티그래비티는 헤드리스(`agy -p`)로 돌리면 "command" 권한이 필요한 도구 호출을 전부 자동 거부하므로(비대화형이라 승인 프롬프트를 못 띄움), 저장소를 직접 못 뒤진다 — 그 제약을 이 단계가 우회한다. 해법은 안 보여주고 "지금 저장소 상태"라는 사실만 보여주는 것이므로 편향 문제 없음.

**이 컨텍스트 번들의 수신자는 안티의 스펙 작성 하나가 아니다** — 코덱스의 반박, 초안경쟁 양쪽(코덱스+안티), 코덱스의 실행까지 전부 같은 컨텍스트를 봐야 의미가 있다. 구현 시 빠뜨리기 쉬운 지점.

## 티어 판정 (컨텍스트 수집 직후, 기계적)

**규칙: 변경 파일 수 ≤ 3개 AND 민감 경로(설정/보안/`.github/workflows`/공개문서) 미포함 → 경량. 그 외 전부 → 전체.**

컨텍스트 수집 단계의 diff 통계만 있으면 판정 가능 — 안티의 스펙이 필요 없으므로, 안티 호출보다 **반드시 먼저** 온다. (v1 개정에서 이 순서를 놓쳐서 안티가 경량 트랙에도 다시 끼어드는 오류가 났었다 — 재발 방지용으로 명시.)

클로드의 재량 판단이 아니라 기계적 대조인 이유: 클로드가 판정 주체면 "일을 피하려는 유인"이 생긴다(Plan 에이전트 지적).

## 경량 트랙

**0/1/2단계 없음.** 클로드가 바로 실행 → 코덱스가 평가.

- 정식 사전 스펙 등록을 안 하는 이유: 경량 트랙의 존재 이유 자체가 "가볍게"이므로, 거기에 정식 절차를 넣으면 경량 트랙이 없어지는 셈.
- 코덱스는 채점 전에 **자신이 판단한 완료조건을 먼저 명시**하고, 그걸 근거로 채점한다 (즉흥성을 최소한으로 감사 가능하게 남겨두는 절충).
- 안티그래비티는 이 트랙에서 **0회 호출**. 이유: `coach --json`으로 실측한 결과 안티그래비티는 사용량 창(quota window)이 안 보임("데이터 부족")인 반면 Codex는 96% 여유가 명확히 보임(당시 기준) — 보이지 않는 자원을 고빈도 트랙에 쓰지 않는다는 의도적 선택.

### 탈출구 (경량→전체 재분류)

정적 규칙(파일 수·경로)은 실행 **전** 예측이라 실제 diff를 보면 틀릴 수 있다. 코덱스가 평가 중 "이건 전체 트랙 감이다"라고 판단하면 관대하게 채점하지 않고 반려할 수 있다. 이 권한을 코덱스(이해관계 없는 제3자)에게 주는 이유: 클로드가 재분류를 판단하면 "일 피하려는 유인" 문제가 재발함.

**발동 조건 (OR — 둘 중 하나만 걸려도 반려):**
1. **기계적 재검사** (모델 호출 없이 계산만): 티어판정에 쓴 규칙(파일수≤3, 민감경로)을 실제 실행 후 diff로 자동 재검사. 위반되면 그 자체로 근거 성립 — 비용 없는 안전장치.
2. **코덱스의 근거 기반 판단**: 규칙은 통과했지만 코덱스가 "개념적으로 크다"고 볼 경우. **"느낌상 크다"는 불가 — 파일 수, 경로, 어떤 파일이 민감경로인지 구체적 사실을 반드시 명시해야 발동 가능.**

**발동 시 처리:** 클로드의 기존 산출물을 **버리지 않고 베이스라인으로 삼는다.** 이 분기에서는 코덱스의 별도 초안 단계를 생략(실물이 이미 있으니 "의견"보다 나은 정보) — **안티만 독립적으로 자기 접근을 제시**하고, 클로드가 "베이스라인 vs 안티 접근"을 비교해 코덱스에게 수정 지시(처음부터 새로 짜라가 아니라 기존 걸 이렇게 보완하라)를 내린다. 이후 흐름(실행→평가→판정)은 전체 트랙과 동일하게 진행.

**최종 보고 시 "경량으로 시작 → 전체로 재분류됨" 사실을 반드시 명시.** 조용히 넘어가지 않는다.

## 전체 트랙

### 0단계 — 기준 고정 (안티그래비티)

입력은 사용자 원 지시문 + 컨텍스트 번들뿐. 코덱스/클로드의 해법·초안은 절대 안 보여줌.

1. 정보 충분성 판단 — 부족하면 역질문(필수 최대 3개 + 선택 최대 3개, 왕복 최대 2회). 그 이상은 아는 만큼 쓰고 "확인 필요"로 남김.
2. 스펙 작성 ("어떻게 할지"는 절대 안 씀): 목표 한 문단 / 산출물(형식·경로) / 제약 / 종료조건(기계적으로 판정 가능한 것만).
3. 채점표 작성 (**고정+동적 혼합**, 안티의 완전 즉흥 창작 아님):
   - **고정 60~70%**: 모든 작업에 항상 적용되는 공통 축 — 정확성 / 완전성(목표 달성 포함) / 안전성(되돌리기 가능성) / 기존 컨벤션 준수. `verify-task.js`의 기존 고정 RUBRIC 패턴 재사용.
   - **동적 30~40%**: 이번 작업 고유의 종료조건만 안티가 추가.
   - 거부권 항목 별도 표시 — 톤(강점/약점 균형) 조절 대상 아니고, 걸리면 점수 무관 반려.

**왜 고정+동적 혼합인가:** 안티가 스펙도 채점표도 채점도 혼자 다 하면(순수 즉흥 채점표), "같은 모델이 자기 기준을 그때그때 옮긴다"는 자기참조 문제가 생긴다(Plan 에이전트가 가장 날카롭게 지적 — 기존 `verify-task.js`가 애초에 고정 rubric을 쓰는 이유가 이걸 막기 위해서였다는 점과 비교). 고정 축을 깔아두면 매 작업 기준이 완전히 흔들리지는 않는다.

**코덱스 1회 반박권:** 안티가 만든 스펙+채점표를 코덱스가 "이거 하나 빠졌다/이 기준 이상하다"고 한 번 지적할 기회(작성은 안 하고 지적만). 나중에 코덱스가 이 채점표로 채점당하는 게 아니라 안티가 채점하므로(4단계), 반박권이 자기방어가 아니라 "피고인이 기소장에 이의 제기하는" 구조 — 순환 논리 아님.

### 1단계 — 초안 경쟁 (코덱스 + 안티그래비티)

0단계 스펙 + 컨텍스트 번들만 보고 각자 독립적으로 접근/의견 제시. 서로 결과 안 봄 (앵커링 편향 방지).

### 2단계 — 종합 (클로드)

두 초안을 비교해 "이 방향으로 가되 이 부분 보완" 정도의 짧은 지시문만 작성(전체를 다시 쓰지 않음). 코덱스에게 전달.

### 3단계 — 실행 (코덱스)

클로드의 지시대로 실제 개선 결과물 작성. **구현 주의: 기존 `score-dispatch.sh`의 코덱스 호출은 채점용 읽기전용(`sandbox: read-only`)이라, 실제로 파일을 쓰는 이 단계는 별도의 쓰기 가능한 호출 경로가 필요하다 — 기존 dispatch 재사용 불가.**

### 4단계 — 평가 (안티그래비티)

0단계 채점표로 결과물 채점 + 치명적 결함 발견 시 점수 무관 즉시 거부권.

**왜 안티가 평가하고 코덱스가 아닌가:** 3단계 실행자가 코덱스이므로, 코덱스가 4단계 평가까지 하면 자기가 만든 걸 자기가 채점하는 꼴이 된다. "작성자와 평가자는 항상 달라야 한다"는 원칙(critique-loop에서 이미 검증된 규율)에 따라 전체 트랙에서는 실행=코덱스, 평가=안티가 고정이다. 안티가 "실행" 역할을 맡은 전례는 이 시스템에도, 참고한 mac-agent 다른 부분에도 없다.

### 5단계 — 최종판정 (클로드)

① 거부권 발동됐나 → 예: 반려, 지적사항을 그대로 코덱스에게 전달해 재시도
② 아니오 → 90점 이상인가 → 예: 승인, 종료 / 아니오: 안티의 지적사항을 그대로 코덱스에게 전달해 재시도

## 왕복 상한 (양 트랙 공통)

3→4→5(또는 경량의 대응 단계) 반복 **최대 2회**. 2회차부터 클로드는 다시 종합하지 않고 안티의 지적을 그대로 전달만(1회차보다 가벼움). 2회 초과해도 통과 못 하면 클로드가 루프를 멈추고, 지금까지의 채점표·지적사항을 그대로 들고 사용자에게 에스컬레이션.

**노이즈 표시:** 왕복 상한 2회는 비용 상한이지 품질 보장이 아니다 — 실측 사례(기존 `verify-task-history.jsonl`에서 거의 동일한 테스트 작업에 안티/Gemini 채점이 0/64/89/92점으로 갈린 전례 있음)를 볼 때, 라운드 간 점수 변동폭이 그 라운드에서 실제로 고쳐진 양(diff 변화량)에 비해 과하게 크면 "통과/탈락"이 아니라 **"측정 노이즈 가능성"**으로 사용자에게 별도 표시한다. 자동으로 확정 짓지 않는다. 정확한 판정 수식(예: diff 변화량 대비 점수 델타 비율의 임계값)은 설계 문제가 아니라 **구현 시 정할 파라미터**로 남겨둔다.

## 인지하고 받아들이는 트레이드오프

- **전체 트랙 비용:** 컨텍스트수집+안티스펙+코덱스반박+초안경쟁(2)+종합+실행+평가(+재시도 최대 2회)까지 합치면 외부 CLI 호출이 최악의 경우 7~9회, 체감 5~15분. 저빈도·수동호출·고위험 전용이라는 전제 하에 "제대로 된 리뷰 한 번"의 값으로 받아들인다.
- **"클로드는 아무것도 직접 작성하지 않는다" 원칙은 기술적 강제가 아니라 규율이다.** `agy`의 헤드리스 샌드박스 거부처럼 시스템이 막는 게 아니라 절차 합의일 뿐 — 클로드가 안 지켜도 아무도 기술적으로 막지 못한다. 이 프로젝트의 다른 규율(예: Task Lifecycle의 task.md 작성 의무)도 같은 성격이라, 새로운 종류의 약점은 아니라고 보고 그대로 받아들인다.

## 아직 안 정해진 것 (구현 시 확정)

- 노이즈 판정의 정확한 수식/임계값.
- 전체 트랙 코덱스 실행(3단계)의 실제 쓰기 가능 호출 경로 설계.
