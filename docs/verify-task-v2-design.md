# verify-task v2 — Claude 최소 세션 기반 다중 검증 게이트 (구현됨, 2026-08-01)

**상태: 구현됨 (`bin/verify-task-orchestrator.py`).** 구형 JS Workflow 어댑터는 제거되었다. 이 문서는 코드가 아니라 결정 기록이다. 2026-07-25~26에 걸쳐 사용자·Claude·Codex·Antigravity·Plan 에이전트가 여러 라운드로 검토하며 나온 최초 설계이고(아래 0~5단계 절, 이후 폐기됨), 결정마다 "왜"를 남긴 이유는 역할과 호출 순서가 개정 때마다 어긋나는 일을 막기 위해서다. 2026-08-01에 전체 트랙이 조사·병렬 계획·코드 리뷰 스킬 흐름으로 재설계되었고, 현재 경량 트랙은 Codex 구현과 Antigravity 독립 리뷰를 사용한다. 문서 하단 최신 개정 섹션이 현재 유효한 설계다. 구현/수정 시 이 문서를 먼저 읽고, 여기 없는 임의 변경은 하지 말 것.

## 목적

기존 `verify-task.js`는 완료된 작업을 Codex+Antigravity 양쪽에 사후 채점만 시킨다(고정 rubric, 85점 통과). v2는 작업 시작 전에 지시문을 정규화하고, Antigravity의 병렬 조사와 Codex의 병렬 계획 검토를 거친 뒤 구현하며, 완료 후 code-review 스킬 계약으로 동일 SHA를 검증한다. 1차안(모든 지시에 5단계 왕복, 즉흥 채점표, 90점 단일기준)은 폐기된 역사적 기록으로 아래에 남겨둔다.

## 적용 범위

일반 대화형 질문·답변은 제외. `.md` 문서 작업, 코드레벨 작업, "파일 정리해줘" 같은 개별 지시까지 포함해 "작업"이라 부를 만한 것 전부.

## 호출 방식: 수동, 훅 아님

Codex·Antigravity·Plan 3자 만장일치 결론. Claude Code의 `UserPromptSubmit` 훅이 실제로 존재하고 프롬프트 처리 전에 개입 가능하다는 것까지 확인했지만(기본 timeout 30초, 연장 가능), 전체 트랙은 최악의 경우 외부 CLI 호출 7~9회로 5~15분이 걸릴 수 있어 사용자를 동기적으로 막는 훅과 구조적으로 안 맞는다. 기존 `verify-task`처럼 **명시적으로 호출하는 워크플로우**로 남긴다.

## 컨텍스트 수집 (첫 단계, 클로드, 기계적)

`git status` / `git diff --stat` / 변경 파일 목록 + **관련 컨벤션 문서(CLAUDE.md 등)** + **테스트 실행 명령**까지 포함. 이게 없으면 뒤에서 안티가 "기존 컨벤션 준수" 항목 자체를 판단할 근거가 없다. 안티그래비티는 헤드리스(`agy -p`)로 돌리면 "command" 권한이 필요한 도구 호출을 전부 자동 거부하므로(비대화형이라 승인 프롬프트를 못 띄움), 저장소를 직접 못 뒤진다 — 그 제약을 이 단계가 우회한다. 해법은 안 보여주고 "지금 저장소 상태"라는 사실만 보여주는 것이므로 편향 문제 없음.

**이 컨텍스트 번들의 수신자는 Antigravity 조사 하나가 아니다** — 병렬 조사, Claude 계획, Codex 계획 검토·수정·실행, code-review 스킬까지 동일한 사실 컨텍스트를 기준으로 삼아야 의미가 있다. 구현 시 빠뜨리기 쉬운 지점.

## 티어 판정 (컨텍스트 수집 직후, 기계적)

**규칙: 변경 파일 수 ≤ 3개 AND 민감 경로(설정/보안/`.github/workflows`/공개문서) 미포함 → 경량. 그 외 전부 → 전체.**

컨텍스트 수집 단계의 diff 통계만 있으면 판정 가능하므로 provider 호출보다 **반드시 먼저** 온다. 경량으로 판정된 뒤에만 Codex 구현과 Antigravity 독립 리뷰를 순서대로 호출한다.

클로드의 재량 판단이 아니라 기계적 대조인 이유: 클로드가 판정 주체면 "일을 피하려는 유인"이 생긴다(Plan 에이전트 지적).

## 경량 트랙

**0/1/2단계 없음.** 코덱스가 바로 실행 → 안티그래비티가 평가.

- 정식 사전 스펙 등록을 안 하는 이유: 경량 트랙의 존재 이유 자체가 "가볍게"이므로, 거기에 정식 절차를 넣으면 경량 트랙이 없어지는 셈.
- 안티그래비티는 실제 diff·하네스 판정·테스트 요약만 근거로 차단 리뷰한다. 점수는 매기지 않는다.
- 안티그래비티는 이 트랙에서 독립 리뷰어로 호출한다. 구현자와 리뷰어를 분리해 메인 세션과 다른 계정을 사용한다.

### 탈출구 (경량→전체 재분류)

정적 규칙(파일 수·경로)은 실행 **전** 예측이라 실제 diff를 보면 틀릴 수 있다. 안티그래비티가 평가 중 "이건 전체 트랙 감이다"라고 판단하면 관대하게 채점하지 않고 반려할 수 있다. 이 권한을 안티그래비티(이해관계 없는 제3자)에게 주는 이유: 코덱스가 재분류를 판단하면 "일 피하려는 유인" 문제가 재발함.

**발동 조건 (OR — 둘 중 하나만 걸려도 반려):**
1. **기계적 재검사** (모델 호출 없이 계산만): 티어판정에 쓴 규칙(파일수≤3, 민감경로)을 실제 실행 후 diff로 자동 재검사. 위반되면 그 자체로 근거 성립 — 비용 없는 안전장치.
2. **안티그래비티의 근거 기반 판단**: 규칙은 통과했지만 안티그래비티가 "개념적으로 크다"고 볼 경우. **"느낌상 크다"는 불가 — 파일 수, 경로, 어떤 파일이 민감경로인지 구체적 사실을 반드시 명시해야 발동 가능.**

**발동 시 처리:** 코덱스의 기존 산출물(라이트 트랙 구현)을 **버리지 않고 베이스라인으로 삼는다.** 전체 트랙 실행자도 이제 코덱스로 동일하므로 별도 재실행이나 초안 재작성 없이 곧바로 전체 트랙의 표준 독립 리뷰 단계(클로드+안티그래비티 각자 리뷰)로 직행한다. 이후 흐름(실행→평가→판정)은 전체 트랙과 동일하게 진행.

**최종 보고 시 "경량으로 시작 → 전체로 재분류됨" 사실을 반드시 명시.** 조용히 넘어가지 않는다.

## 전체 트랙

⚠️ **2026-07-27 개정: 아래 0~5단계(채점표 기반)는 폐기됨.** 하네스 기반 정성 검토로 대체됨 — 문서 하단 "## 개정 (2026-07-27)" 섹션 참고. 이 절은 과거 결정 기록으로 그대로 남겨두되, 구현 시 아래 내용을 따르지 말 것.

### 0단계 — 기준 고정 (안티그래비티) [폐기됨]

입력은 사용자 원 지시문 + 컨텍스트 번들뿐. 코덱스/클로드의 해법·초안은 절대 안 보여줌.

1. 정보 충분성 판단 — 부족하면 역질문(필수 최대 3개 + 선택 최대 3개, 왕복 최대 2회). 그 이상은 아는 만큼 쓰고 "확인 필요"로 남김.
2. 스펙 작성 ("어떻게 할지"는 절대 안 씀): 목표 한 문단 / 산출물(형식·경로) / 제약 / 종료조건(기계적으로 판정 가능한 것만).
3. 채점표 작성 (**고정+동적 혼합**, 안티의 완전 즉흥 창작 아님):
   - **고정 60~70%**: 모든 작업에 항상 적용되는 공통 축 — 정확성 / 완전성(목표 달성 포함) / 안전성(되돌리기 가능성) / 기존 컨벤션 준수. `verify-task.js`의 기존 고정 RUBRIC 패턴 재사용.
   - **동적 30~40%**: 이번 작업 고유의 종료조건만 안티가 추가.
   - 거부권 항목 별도 표시 — 톤(강점/약점 균형) 조절 대상 아니고, 걸리면 점수 무관 반려.

**왜 고정+동적 혼합인가:** 안티가 스펙도 채점표도 채점도 혼자 다 하면(순수 즉흥 채점표), "같은 모델이 자기 기준을 그때그때 옮긴다"는 자기참조 문제가 생긴다(Plan 에이전트가 가장 날카롭게 지적 — 기존 `verify-task.js`가 애초에 고정 rubric을 쓰는 이유가 이걸 막기 위해서였다는 점과 비교). 고정 축을 깔아두면 매 작업 기준이 완전히 흔들리지는 않는다.

**코덱스 1회 반박권:** 안티가 만든 스펙+채점표를 코덱스가 "이거 하나 빠졌다/이 기준 이상하다"고 한 번 지적할 기회(작성은 안 하고 지적만). 나중에 코덱스가 이 채점표로 채점당하는 게 아니라 안티가 채점하므로(4단계), 반박권이 자기방어가 아니라 "피고인이 기소장에 이의 제기하는" 구조 — 순환 논리 아님.

### 1단계 — 초안 경쟁 (코덱스 + 안티그래비티)

0단계 스펙 + 컨텍스트 번들만 보고 각자 독립적으로 접근/의견 제시. 서로 결과 안 봄 (앵커링 편향 방지).

### 2단계 — 종합 (클로드)

두 초안을 비교해 "이 방향으로 가되 이 부분 보완" 정도의 짧은 지시문만 작성(전체를 다시 쓰지 않음). 코덱스에게 전달.

### 3단계 — 실행 (코덱스)

클로드의 지시대로 실제 개선 결과물 작성. **구현 주의: 기존 `score-dispatch.sh`의 코덱스 호출은 채점용 읽기전용(`sandbox: read-only`)이라, 실제로 파일을 쓰는 이 단계는 별도의 쓰기 가능한 호출 경로가 필요하다 — 기존 dispatch 재사용 불가.**

### 4단계 — 평가 (안티그래비티)

0단계 채점표로 결과물 채점 + 치명적 결함 발견 시 점수 무관 즉시 거부권.

**왜 안티가 평가하고 코덱스가 아닌가:** 3단계 실행자가 코덱스이므로, 코덱스가 4단계 평가까지 하면 자기가 만든 걸 자기가 채점하는 꼴이 된다. "작성자와 평가자는 항상 달라야 한다"는 원칙(critique-loop에서 이미 검증된 규율)에 따라 전체 트랙에서는 실행=코덱스, 평가=안티가 고정이다. 안티가 "실행" 역할을 맡은 전례는 이 시스템에도, 참고한 mac-agent 다른 부분에도 없다.

### 5단계 — 최종판정 (클로드)

① 거부권 발동됐나 → 예: 반려, 지적사항을 그대로 코덱스에게 전달해 재시도
② 아니오 → 90점 이상인가 → 예: 승인, 종료 / 아니오: 안티의 지적사항을 그대로 코덱스에게 전달해 재시도

## 왕복 상한 (양 트랙 공통)

3→4→5(또는 경량의 대응 단계) 반복 **최대 2회**. 2회차부터 클로드는 다시 종합하지 않고 안티의 지적을 그대로 전달만(1회차보다 가벼움). 2회 초과해도 통과 못 하면 클로드가 루프를 멈추고, 지금까지의 채점표·지적사항을 그대로 들고 사용자에게 에스컬레이션.

**노이즈 표시:** 왕복 상한 2회는 비용 상한이지 품질 보장이 아니다 — 실측 사례(기존 `verify-task-history.jsonl`에서 거의 동일한 테스트 작업에 안티/Gemini 채점이 0/64/89/92점으로 갈린 전례 있음)를 볼 때, 라운드 간 점수 변동폭이 그 라운드에서 실제로 고쳐진 양(diff 변화량)에 비해 과하게 크면 "통과/탈락"이 아니라 **"측정 노이즈 가능성"**으로 사용자에게 별도 표시한다. 자동으로 확정 짓지 않는다. 정확한 판정 수식(예: diff 변화량 대비 점수 델타 비율의 임계값)은 설계 문제가 아니라 **구현 시 정할 파라미터**로 남겨둔다.

## 인지하고 받아들이는 트레이드오프

- **전체 트랙 비용:** 컨텍스트수집+안티스펙+코덱스반박+초안경쟁(2)+종합+실행+평가(+재시도 최대 2회)까지 합치면 외부 CLI 호출이 최악의 경우 7~9회, 체감 5~15분. 저빈도·수동호출·고위험 전용이라는 전제 하에 "제대로 된 리뷰 한 번"의 값으로 받아들인다.
- **"클로드는 아무것도 직접 작성하지 않는다" 원칙은 기술적 강제가 아니라 규율이다.** `agy`의 헤드리스 샌드박스 거부처럼 시스템이 막는 게 아니라 절차 합의일 뿐 — 클로드가 안 지켜도 아무도 기술적으로 막지 못한다. 이 프로젝트의 다른 규율(예: Task Lifecycle의 task.md 작성 의무)도 같은 성격이라, 새로운 종류의 약점은 아니라고 보고 그대로 받아들인다.

- **기록 시점**: (1) 사전비평 단계 — 코덱스 취합(`codexReconcile`)이 낸 `compiledIssues`, (2) 코드 리뷰 단계 — 코덱스+안티가 실제 diff에서 낸 이슈. 둘 다 누적 대상.

- **핵심 제약 — 코덱스는 이 파일을 직접 못 읽는다:** `score-dispatch.sh`의 코덱스 호출엔 `-C`(대상 저장소 경로)가 없어 애초에 어떤 저장소도 못 보고, `codex-execute-dispatch.sh`의 `-C`는 mac-agent가 아니라 **대상 프로젝트** 디렉토리다. 그래서 "코덱스야 이 파일을 읽어라"라고 시켜도 코덱스는 접근할 수 없다. 대신 매번 `agent()`를 감싸는 Claude 서브에이전트가(진짜 Read 툴이 있으므로) 하네스 파일을 먼저 읽어서, 그 내용을 프롬프트 텍스트 맨 앞에 직접 박아 넣은 뒤 코덱스에게 전달한다(`buildScoreDispatchInstruction`/`buildExecuteDispatchInstruction`의 하네스 prepend 로직). 안티그래비티 호출에는 하네스를 주입하지 않음 — 하네스는 코덱스 전용.

### 부재 주장 게이트

하네스는 현재 셸이나 단일 경로를 확인한 뒤 전역 부재로 확대하는 오류를 차단한다.
`bin/edge_agent_capability_preflight.py`는 실행파일·환경변수 이름·보안 저장소·LaunchAgents·
설정 디렉터리를 읽기 전용으로 조사하고, 비밀값은 읽지 않은 채 `discovery_evidence`를 만든다.
`bin/edge_agent_absence_guard.py`는 토큰·키·자격증명·설정·파일·서비스·실행파일·기능의
부재 주장이 `discovery_evidence` 또는 `searched_scopes`를 포함하지 않으면 provider 결과를
실패 처리한다. 허용되는 표현은 전역 “없음”이 아니라 “검색한 범위에서 찾지 못함”이다.

경량 트랙은 `Codex 구현 → 하네스 diff·테스트 → Antigravity 차단 리뷰`만 수행한다.
파일 3개 초과, 민감·보호 경로, 신규 의존성, 마이그레이션·배포·파괴적 데이터 변경,
공개 API 파괴 변경, 전체 검증 명시가 있으면 하네스가 전체 트랙으로 격상한다.

전체 트랙은 `Antigravity 병렬 조사 → Codex 계획·구현 → Codex 자기점검·하네스 테스트
→ Claude 독립 리뷰 + Antigravity 독립 리뷰 → Codex 수정 → 리뷰 재검증` 순서다.
Claude는 기본적으로 계획·조사·구현을 맡지 않으며, 계획 비평은 별도 고위험 조건에서만
추가한다. Codex 자기점검은 독립 리뷰어 슬롯으로 계산하지 않는다.

리뷰 입력은 원 작업, 최종 계획, 관련 파일, 적용 규칙, 현재 diff, 테스트 요약으로
제한한다. 전체 로그는 `logs/`에 보존하고 리뷰어에는 실패 요약만 전달한다. 실행별
`task.json`, `repository-state.json`, `investigation.json`, `current.diff`,
`test-summary.json`, `metrics.jsonl`을 남겨 후속 재시도와 토큰 분석에 사용한다.

Antigravity의 `agy -p` 조사·리뷰는 headless 권한 프롬프트를 표시할 수 없으므로
저장소 탐색을 요청하지 않는다. 호스트 하네스가 조사 단계에는 허용된 관련 파일 내용
(파일당 12,000자, 전체 24,000자)과 규칙(6,000자)을 미리 수집하고, 리뷰 단계에는
중복 파일 내용을 보내지 않고 현재 diff와 테스트 요약만 전달한다. Antigravity 프롬프트에는
도구·명령·테스트 실행 금지 계약을 명시한다. 권한 우회 플래그는 사용하지 않으며, 증거가
부족하거나 provider가 JSON을 반환하지 않으면 `dispatchFailed`로 기록하고 승인하지 않는다.
커밋 SHA 기반 `code-review-request-worker`도 동일하게 호스트가 stat·diff·변경 파일 내용을
미리 묶어 Antigravity에 전달하며, diff는 40,000자, 파일 증거는 전체 24,000자로 제한한다.
리뷰 sandbox는 Antigravity CLI가 실제로 사용하는 기본 로그·crash 경로를 제거하지 않고
동적 로그 경로와 함께 허용한다. 이 경로를 제거하면 인증 초기화가 실패해 headless 리뷰가
빈 응답으로 끝날 수 있다.
작업 명세가 테스트 보강을 요구하지만 테스트 경로를 직접 지정하지 않은 경우에는 하네스가
작업 대상 파일명과 basename이 일치하는 기존 테스트 파일만 허용 목록에 추가한다. 또한
provider 응답에서 중첩 배열·객체를 최종 결과로 오인하지 않도록 오케스트레이터 JSON 추출기는
완전한 top-level JSON 값 단위로 후보를 수집한다.

하네스 테스트 명령은 `package.json`/`Makefile`의 `test`, `lint`, `typecheck`를 모두
실행하고, 명시된 실행기가 없으면 pytest 설정과 실제 설치 여부를 확인한 뒤 Python
`unittest` 및 Node `--test`를 탐지한다. 각 명령의 결과와 통합 로그를 `test-summary.json`
에 기록하며, 정상 테스트 이름의 `failed` 문자열은 실패로 오인하지 않는다. 결정론적 하네스와
provider CLI는 `bin/verify-task-orchestrator.py`가 호스트 subprocess로 직접 실행한다. 따라서
Claude 세션은 작업을 전달하는 부모 세션과 필요한 역할의 단발 CLI 호출로 제한되고, 별도
Claude Workflow `agent()` 세션은 기본 경로에 사용하지 않는다.

이 경로에는 별도 provider API 키가 필요하지 않다. `claude`, `codex`, `agy`가 각각 로그인된
구독형 CLI인지 하네스가 사전 확인하고, 실제 인증·사용량 정책은 각 CLI 계정에 맡긴다.
브리지와 provider dispatch가 실제 provider 토큰 사용량을 알 수 없는 경우 해당 값은 `0`이
아니라 `null`로 기록하고, 입력 패키지 바이트와 추정 토큰만 별도로 남긴다.

### 폐기된 직전 개정 흐름

다음 내용은 구현 전 설계 기록이며 현재 실행 경로가 아니다.

1. Claude가 사용자 지시문을 `normalizedPrompt`, 조사 브리프, 완료 조건, 제약으로 정규화한다.
2. Antigravity가 저장소 구조, 의존성·공식 자료, 위험·테스트의 세 초점을 서로 독립적으로 병렬 조사한다. 조사 실패는 빈 결과로 대체하지 않는다.
3. Claude가 조사 결과를 통합해 `parallelTasks`, `dependsOn`, 파일 소유권, 통합 단계, 테스트 계획을 포함한 병렬 코딩 계획을 작성한다.
4. Codex가 아키텍처·의존성·파일 충돌과 구현 가능성·엣지케이스·테스트의 두 초점을 병렬 검토한다.
5. Codex가 두 검토 결과를 취합하고 반박 근거를 남긴 뒤 최종 구현 계획을 수정한다. 이슈는 `docs/codex-harness.md`에 append-only로 누적한다.
6. Codex가 최종 계획에 따라 코딩한다. 실행 성공 응답이 없으면 코드 리뷰로 진행하지 않는다.
7. 코딩 완료 후 code-review 스킬 계약을 발동한다. Codex가 1차 리뷰하고 Antigravity가 동일한 `head_sha`를 독립 검증한다. 결정론적 검사가 실행되지 않았거나 실패하면 승인하지 않는다.

읽기 전용 조사·계획 검토만 병렬 실행한다. 실제 파일 쓰기는 Codex 실행 단계에서 계획의 파일 소유권과 의존성 경계를 지킨다. 현재 경량→전체 탈출구는 이미 Codex가 만든 baseline을 보존하고 사전 단계는 생략한 뒤 Claude+Antigravity 표준 독립 리뷰로 직행한다.

### 이전 개정 기록 (2026-07-27)

**배경**: 사용자가 원하는 새 흐름은 "코덱스가 스스로 프롬프트/계획을 작성 → 독립 리뷰어와 안티그래비티가 그 계획을 블라인드로 비평 → 코덱스가 비평을 취합·객관적으로 판단해 계획 개선 → 실행 → 코덱스와 안티그래비티가 완성된 코드를 (점수 없이) 둘 다 검수 → 결함은 하네스 문서에 영구 누적"이다. 특히 **"기존 채점표는 사용하지 않음. 무시"**가 확정 지시였으며, 위 0~5단계의 안티 스펙+고정/동적 rubric+90점 임계값 전체를 대체한다.

**당시 적용 범위(현재는 폐기됨)**: 전체(full) 트랙에만 적용했고, 당시 경량(light) 트랙은 파일≤3·비민감경로에서 Claude 실행과 Codex 90점 채점을 유지했다. 현재 경량 계약은 이 역할과 채점 방식을 사용하지 않는다.

**새 흐름 (9단계, 사용자 원 서술 기준)**:
1. 클로드가 사용자 원 지시문을 코덱스에게 그대로 전달.
2. 코덱스가 자기 실행 계획(프롬프트)을 직접 작성.
3. 코덱스가 (원 지시문 + 자기 계획)을 클로드와 안티그래비티 양쪽에 분석 요청.
4. 독립 리뷰어와 안티그래비티가 각각 독립적으로(서로 결과 안 보고 — 기존 "초안경쟁... 앵커링 편향 방지" 원칙 재사용) 계획을 비평.
5. 둘의 비평이 코덱스에게 전달됨.
6. 코덱스가 두 비평에서 나온 버그/결함/오류를 정리(compile).
7. 클로드가 그 정리된 목록을 받아 `docs/codex-harness.md`에 영구 규칙으로 반영.
8. 코덱스가 두 분석을 객관적으로 평가(전부 수용 의무 없음, 반박 가능)하고, 하네스를 참고해 계획을 개선한 뒤 실행(코딩) 시작.
9. 코딩 완료 후 코덱스+안티그래비티가 각각 독립적으로 실제 diff를 무점수로 리뷰. 어느 한쪽이라도 blocking 이슈를 찾으면 반려 → 이슈를 코덱스에게 전달해 재시도(기존 왕복 상한 최대 2회, 초과 시 사용자 에스컬레이션 그대로 유지). 둘 다 blocking 이슈 없으면 통과. 이 단계에서 발견된 결함도 하네스에 누적한다.

**구현 시 내린 결정 두 가지 (문자 그대로의 9단계와 다른 부분, 명시적으로 남김):**
- **5+6+8단계를 코덱스 호출 하나(`codexReconcile`)로 병합.** 이유: 클로드의 하네스 반영(7단계)은 "다음 실행부터" 코덱스가 참고하라는 것이지, 이번 실행 중 코덱스가 자기가 방금 만든 규칙을 다시 읽어야 할 이유가 없음 — 코덱스는 이미 원본 비평 텍스트를 그대로 받으므로 병합해도 정보 손실이 없고, 외부 CLI 왕복을 1회 줄인다.
- **`needsClarification`(정보 부족 시 역질문) 판단 주체를 코덱스로 이동.** 옛 0단계(안티 스펙 작성)가 없어지면서 이 판단을 할 자리가 사라졌는데, 사용자 원 지시문을 처음 받아 계획을 세우는 코덱스(1단계, `codexOwnPlan`)가 자연스러운 자리라고 판단해 그쪽에 흡수시킴 — 사용자에게 별도 확인 안 받은 구현 판단.
