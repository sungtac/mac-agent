# work-log-stop-check.sh (일정비서 — session-end archiving + calendar logging)

`hooks/work-log-stop-check.sh` — a Claude Code `Stop` hook. Registered in `~/.claude/settings.json` under `hooks.Stop` (second entry, alongside `verify-task-stop-check.sh`). On every session end, if the session made at least one Edit/Write call (cheap mechanical gate), it backgrounds a headless `claude -p` sub-call that reads the session transcript and decides whether the session was public/work-output (document writing, etc.) as opposed to meta work (building/editing Claude Code hooks/skills/workflows — including this automation itself) or private use. Ambiguous cases are told to SKIP — under-logging beats spamming the calendar.

- **If public work output:** the sub-agent copies the session's created/edited output files into `~/Library/CloudStorage/GoogleDrive-sungtac@gmail.com/내 드라이브/업무아카이브/YYYY-MM-DD/` (copy, not move — originals stay put) and creates one Google Calendar event per session on `sungtac@gmail.com` (30 min, today, description = short summary + file list). This is deliberately per-session, not one cumulative daily event.
- **Why background instead of an inline `type: "agent"` Stop hook:** Claude Code's `Stop` hooks do support `type: "agent"` (a real subagent, not just `command`/shell — see the correction in [verify-task-stop-check.md](verify-task-stop-check.md)), so inline LLM judgment is technically possible now. Not used here anyway: an inline agent-type hook still has to resolve before the `Stop` event completes, so the user's session would sit blocked for however long the classification+archiving round trip takes (10-60s observed). Backgrounding a headless `claude -p` call (`nohup ... &`, `disown`) from a `command` hook lets the hook return near-instantly and the user's session end immediately, with the real work continuing fully detached afterward — a property an inline agent-type hook doesn't get for free. Confirmed via manual test that headless `claude -p` (no special flags — ambient `permissions.defaultMode: "auto"` from settings.json is enough) has full access to the same claude.ai-connected MCP tools (Calendar/Drive) as an interactive session.
- **Recursion guard:** the backgrounded `claude -p` call is itself a Claude Code session and will fire its own `Stop` event when it finishes. The dispatch sets `WORK_LOG_DISPATCHED=1` in that subprocess's environment; the script exits immediately at the top if that var is set. Without this it would re-trigger itself forever. Verified empirically the recursion guard and the "no Edit/Write → exit early" gate are both real no-ops (no marker file, no background process spawned).
- **Verified:** the SKIP path end-to-end twice — once feeding it the transcript of the session that built this very hook (correctly classified as meta work, SKIPped), and again with a synthetic transcript deliberately labeled as test data (correctly self-identified as test/meta and SKIPped even though the fake content superficially looked like a real memo — good judgment). Both confirmed the background dispatch itself completes normally (well under a minute) — this hook's dispatch runs as a child of the interactive `claude` process handling the Stop event, not launchd, so it hasn't itself been observed to hang the way [weekly-report.md](weekly-report.md)'s launchd-triggered dispatch has. **The actual LOGGED path (real file copy + real Calendar event, triggered automatically by the hook itself rather than done manually) has never been directly observed end-to-end** — every real work session so far (the phone recording, the KakaoTalk chat log) was archived/logged manually in-session instead, with the hook's dispatch marker pre-touched to skip its own redundant pass. Worth doing a real unforced end-to-end LOGGED-path test at some point.
- **Watchdog added defensively (2026-07-25):** this dispatch had zero timeout protection even after the intermittent `claude -p` hang was confirmed in `weekly-report.sh` — a real gap, since unlike the weekly job (checked once a week by a human) a silent hang here would just accumulate one stuck ~500MB `claude` process per qualifying session, invisibly, forever. Added the same watchdog shape: 300s timeout, `SIGTERM` → 2s grace → `pkill -9 -P` (reap any already-spawned MCP-server children by PPID, since the backgrounded process shares this script's process group) → `SIGKILL`, `--debug-file` kept only on timeout. A timeout now shows up as `TIMEOUT after 300s` in `~/.claude/hooks-state/work-log/<session-id>.log` instead of silently vanishing.
- **Discord reply-triggered retry (Phase 2.5, 2026-07-28):** the "no retry loop, blind retry could duplicate Calendar events/archive files" concern above was real but only half-true — archive copy was already idempotent (same source filename → same destination path just overwrites), the actual duplicate risk was Calendar-event-creation alone. Fixed with a `search_events`-before-create guard keyed on a `[세션ID: <id>]` marker embedded in the event description (same idea as `weekly-report.sh`'s guard), plus notification on every terminal outcome (success/failure, not just timeout) so a Discord reply can now safely re-trigger this hook for one specific session. Full design: [discord-bot.md](discord-bot.md) "## Phase 2.5".
- **Known gaps:** (1) macOS has no `timeout(1)` — don't rely on it in scripts here, use the Bash tool's own timeout or a background+poll pattern instead. (2) A separate "new recording files organized automatically" use case (recordings synced from phone/recorder to a folder, independent of any Claude Code session) is explicitly OUT of scope for this hook — no Stop event exists to hook into. (3) A session that's genuinely *mixed* — real work bundled together with meta/automation-building in the same conversation — only gets one classification for the whole session, since the classifier prompt asks for a single (a)/(b)/(c)/(d) label. Coarse-grained by design; a session like that needs manual handling (as done for this one) rather than relying on the hook.
- To port to another agent/machine: add the matching `hooks.Stop` entry (command: `bash <path-to-this-repo>/hooks/work-log-stop-check.sh`) to that machine's `~/.claude/settings.json`, alongside the verify-task entry. Assumes the same Drive-synced path and `sungtac@gmail.com` Calendar — adjust both if the account differs.

Also blocked machine-wide: the Google Drive MCP connector (`mcp__claude_ai_Google_Drive__*`, 8 tools) is authenticated as a third party's account (`sungwan777@gmail.com`), not the user's own — hard-denied via `permissions.deny` in `~/.claude/settings.json`. See [weekly-report.md](weekly-report.md) for the full story (a cloud Routine accidentally wrote a real doc into that stranger's Drive before this was caught).
