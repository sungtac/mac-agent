# weekly-report.sh (일정비서 — Thursday summary report)

`cron/weekly-report.sh` — runs every Thursday via a macOS `launchd` LaunchAgent (`~/Library/LaunchAgents/com.macagent.weekly-report.plist`, label `com.macagent.weekly-report`, `Weekday: 4, Hour: 18, Minute: 0` local time — moved from Friday 18:07 on 2026-07-26 at the user's request). Computes the current Mon–Fri range (robust to running a day early/late off-schedule — derives Monday from `date +%u`, not a hardcoded day offset; the offset math already produces the correct upcoming Friday even when "today" is Thursday, no changes needed for the schedule move), pulls that week's events from Google Calendar (`sungtac@gmail.com`) via a headless `claude -p` call, cross-checks the `업무아카이브` folder for the same week, and writes a two-section report ("이번 주 한 일" / "다음 주 할 일 (제안)", the latter explicitly labeled as a non-committal draft) to `~/Library/CloudStorage/GoogleDrive-sungtac@gmail.com/내 드라이브/주간보고서/YYYY-MM-DD~YYYY-MM-DD/[주간 업무 보고] YYYY년 M월 D일 ~ YYYY년 M월 D일.md` — matching a pre-existing manual folder/naming convention found in that Drive account (last used 2025-09, now resumed). **Also** (added 2026-07-26) creates a matching Google Calendar event on that week's Friday, 09:00–09:30, same title, description = both report sections verbatim + a pointer to the full Drive file path — so the report is visible directly on the calendar, not only in a Drive folder buried under a date-range subfolder.

- **Known trade-off of Thursday 18:00 vs. the old Friday 18:07:** the report is generated a day before the week technically ends, so whatever happens on Friday itself (the week's own last day) can't be in "이번 주 한 일" — it hasn't happened yet at generation time. Accepted knowingly per the user's explicit request, not an oversight.

- **Why launchd instead of a claude.ai cloud Routine:** a cloud Routine was tried first but requires the claude.ai Google Drive MCP connector — which turned out to be authenticated as a third party's account (`sungwan777@gmail.com`), not the user's own. A live test run created a real doc in that stranger's Drive before this was caught (id `1Ojl8R0zdM4XC8IxCrurD8_WcyPgdsf3LAFZbjNUT79E`, undeletable — no delete tool on that MCP connector); the routine (`trig_017yxKuX6SdAF1hV4NGo4rNm`) was disabled via `RemoteTrigger`. Per the user's explicit instruction, all 8 `mcp__claude_ai_Google_Drive__*` tool names are now hard-blocked machine-wide via `permissions.deny` in `~/.claude/settings.json` (verified: the tools disappear entirely, not just error on call). `weekly-report.sh` was built specifically to route around this — it never touches Drive MCP, only Calendar MCP (which IS correctly on `sungtac@gmail.com`) plus local filesystem writes into the already-`sungtac`-owned synced folder. launchd runs persistently on this always-on Mac (33+ days uptime observed) with no expiry, unlike Claude's session-scoped `CronCreate` tool or a claude.ai Routine.
- **Known limitation:** without Drive MCP, the report is saved as a plain `.md` file, not auto-converted to a native Google Doc (`.gdoc`) the way the old manually-created reports in that folder are — conversion on upload requires the Drive API. Acceptable trade-off given the account issue above; revisit if the Drive MCP connector is ever reconnected to `sungtac@gmail.com`.
- **Intermittent launchd hang, root cause narrowed (2026-07-25):** the exact same `claude -p ...` invocation that completes in well under a minute when run directly sometimes hangs when triggered through the real `launchd` path — but **not deterministically**: it hung 3x in a row earlier the same day, then a manual `launchctl kickstart` retry later that same evening completed cleanly (real report written, `exit=0`). Live-inspected a hung process with `lsof`/`netstat -an`/`sample`: ~16-17 TCP connections to `api.anthropic.com` sit `ESTABLISHED` with **empty Send-Q/Recv-Q on both sides** (confirmed via `netstat -an -p tcp`) and near-zero CPU — i.e. the TCP/TLS layer is fine (no dropped packets, no retransmit backlog), the stall is inside the `claude` CLI's own HTTP connection pool (the binary is Bun-based — `sample` shows `Bun Pool 0-3` threads). Ruled out as causes: DNS/proxy (no proxy configured, `scutil --proxy` clean), Tailscale (network extension is active on this Mac but `ExitNodeID` is empty — general egress traffic routes via `en0`, not the tailnet), and (from the earlier round of testing) auth/env/stdin. Given it's intermittent and the binary is closed-source/stripped, further root-causing the Bun HTTP client internals isn't practical from outside — **mitigated via retry instead of fixed**.
- **Current mitigation:** the watchdog-per-attempt timeout was shortened from 600s to 240s (a hang shows zero progress within the first ~30s, so 4 minutes is generous before giving up) and wrapped in a retry loop, `MAX_ATTEMPTS=3`, 5s pause between attempts. Each attempt runs with `--debug-file "$STATE_DIR/${TODAY}-attempt${N}-debug.log"`; the debug log is deleted on success and kept on any failed attempt (timeout or non-zero exit), so if a future Friday run exhausts all 3 attempts, the debug log(s) will have real internals to investigate instead of guessing again. On timeout, the process is sent `SIGTERM` first (grace period to flush the debug log and let it ask any already-spawned MCP-server child processes to exit) before `SIGKILL`; leftover children are then explicitly reaped by PPID (`pkill -9 -P`) since the backgrounded `claude` process shares the script's own process group (no job control in a non-interactive script) — a bare `kill -9 "$CLAUDE_PID"` would only kill `claude` itself and silently orphan any MCP-server subprocess already spawned. Only if all 3 attempts fail does the job log `all 3 attempts failed.` and exit 1 with no report produced.
- **Verified:** running the script directly via `bash cron/weekly-report.sh` (not through launchd) completed correctly multiple times — correct calendar data pulled, correct file path/naming produced. The launchd-triggered path has now also completed successfully at least once (2026-07-25, live repro via `launchctl kickstart`) — the hang is real but intermittent, not a hard block on launchd itself.
- To port to another agent/machine: copy `cron/weekly-report.sh` and adapt the plist's `ProgramArguments` path and the script's `DRIVE_ROOT`/`CALENDAR_ID` if the account differs; `launchctl bootstrap gui/$(id -u) <plist path>` to load. Be aware the intermittent launchd-hang above may or may not reproduce on a different machine — the retry mitigation should absorb it regardless.
