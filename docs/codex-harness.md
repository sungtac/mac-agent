# Codex Harness — 누적 규칙

이 문서는 verify-task-v2 워크플로우가 발견한 결함/버그/오류를 코덱스가 앞으로 참고할 규칙으로 영구 누적한 것이다. append-only — 기존 규칙은 절대 삭제·수정하지 말 것.

## 규칙 목록
- 사용자에게 "…로 전환합니다/진행합니다" 같은 진행 안내 메시지를 보내기 전에, 뒤이어 호출할 함수 내부에 취소·중지 플래그(예: STOP_REQUESTED)로 인한 조기 리턴 경로가 있는지 확인하고, 메시지 전송 지점에서도 동일한 플래그를 먼저 체크해야 한다. 그렇지 않으면 사용자에게는 "전환한다"고 말해놓고 실제로는 아무 동작도 하지 않는 안내-실동작 불일치가 생긴다. (출처: code-review-of-claude-baseline)
- asyncio(또는 유사 비동기 프로세스 API)의 Process.communicate()는 동일 proc 객체에 대해 두 번 호출하지 않는다. 타임아웃/그룹킬 이후 잔여 출력을 추가로 회수해야 한다면 재호출 지점을 try/except로 감싸 파이프가 이미 닫힌 상태에서 발생할 수 있는 예외(ValueError/OSError 등)가 상위로 전파되지 않도록 처리해야 한다. (출처: code-review-of-claude-baseline)
- 동일한 진행 콜백(on_wait 등)을 여러 CLI 호출 지점(예: 작성 단계, 검증 단계)에서 사용하는 워크플로우는, 모든 호출 지점에 일관되게 콜백을 전달해야 한다. 일부 호출에만 전달하면 다른 단계에서 진행 상황 안내가 갱신되지 않아 사용자에게는 멈춘 것처럼 보이는 UX 불일치가 생긴다. (출처: code-review-of-claude-baseline)
- 여러 라운드에 걸쳐 순차적으로 CLI를 호출하며 전역 락(BUSY_LOCK 등)을 쥐는 워크플로우를 설계할 때는, (라운드 수 × 호출당 최대 타임아웃)으로 최악의 경우 총 블로킹 시간을 미리 계산하고, 실사용 환경(예: 그룹 채팅에서 다른 메시지가 대기)에서 그 지연이 허용 가능한지 라이브 트래픽 테스트 전에 반드시 확인해야 한다. (출처: code-review-of-claude-baseline)
- 특정 작업 유형(예: 코딩 작업) 여부를 키워드 매칭으로 휴리스틱 판별할 때는, '수정'/'오류'/'에러'/'커밋'처럼 일상 언어에서도 흔히 쓰이는 범용 단어를 키워드로 넣으면 무관한 요청에서도 오탐이 발생할 수 있음을 인지하고, 그 오탐이 허용 가능한 트레이드오프인지 명시적인 설계 결정으로 남겨야 한다. (출처: code-review-of-claude-baseline)
- 루프 반복 횟수를 환경변수 등 외부 설정으로 조절 가능하게 만들 때는, 값이 0 이하로 잘못 설정되어 루프가 한 번도 실행되지 않는 경우를 대비해 결과 변수의 초기값(예: 사용자 원본 입력 그대로)이 그대로 최종 출력에 노출되지 않도록 방어 코드를 넣거나 최소 1회 실행을 강제해야 한다. (출처: code-review-of-claude-baseline)
- 문서에서 '권장(recommended)' 경로로 절차를 제시할 때는, 그 경로가 실제로 격리(예: git worktree 생성 등 선행 단계) 호출을 거치는지 확인해야 한다. 확인 없이는 권장 경로임에도 작업 격리가 누락될 수 있다. (출처: pre-execution)
- 여러 파일에 걸쳐 동일한 개념(도구·역할 호출 문법 등)의 표현을 바꿀 때는 관련된 모든 템플릿/파일을 함께 갱신해야 한다. 일부만 갱신하면 파일 간 용어가 불일치하게 된다. (출처: pre-execution)
- 문서나 계획에서 특정 도구·기능의 이름을 언급하며 그것을 전제로 재작성할 때는, 그 도구가 현재 하네스/환경에 실제로 존재하고 호출 가능한지 먼저 검증해야 한다. 존재 여부를 확인하지 않으면 재작성의 핵심 전제 자체가 성립하지 않을 수 있다. (출처: pre-execution)
- 공백 오류 등을 git diff --check로 검사할 때는 untracked 상태인 신규 파일이 검사 대상에서 빠질 수 있음을 인지하고, git add 후 검사하거나 신규 파일도 포함하는 별도 방법을 사용해야 한다. (출처: pre-execution)
- 작업 지시에 명시된 정확한 변경 범위(diff scope)를 넘어서는 수정이 필요해지면, 범위 확대를 암묵적으로 진행하지 말고 그 사실을 명시적으로 판단하고 보고해야 한다. (출처: pre-execution)
- CLI 도구에 dry-run이나 비파괴 옵션이 있다고 계획에만 의존해 가정하지 말고, 실행 전에 --help나 소스코드로 해당 플래그가 실제로 존재하는지 확인해야 한다. 존재하지 않는 옵션을 전제로 세운 계획은 의도치 않은 파괴적 실행으로 이어질 수 있다. (출처: pre-execution)
- 원격/원본 소스로 로컬 파일을 교체하는 --yes류 비대화식 설치·동기화 명령을 실행하기 전에는, 로컬 작업 사본(특히 아직 커밋되지 않은 변경)이 덮어써질 위험이 없는지 먼저 확인해야 한다. (출처: pre-execution)
- 파일 내 특정 문구나 패턴을 수정할 때는 grep 등으로 같은 문구가 파일 내 다른 위치에도 중복 존재하는지 먼저 확인하고, 발견된 모든 위치를 함께 갱신해야 한다. (출처: pre-execution)
- 테이블/목록(예: EXCLUDED 항목 등)에 여러 항목을 추가해 개수가 바뀌는 diff를 만들 때는, 그 개수·예시를 언급하는 다른 문서 문구(예: "현재 N개"류의 단수·특정 개수 표현)도 함께 최신화해야 한다. 해당 문구가 있는 파일이 이번 diff의 편집 대상에 포함되지 않았다는 이유만으로 방치하면 문서와 실제 데이터가 불일치한 채로 남는다. (출처: code-review)
- 검증 계획을 세울 때는 저장소 컨텍스트에 기록된 과거 실패(예: 테스트 실패)가 현재 시점 재실행에서는 재현되지 않을 수 있음을 전제하고, "재실행 결과가 이전 실패와 다르게 전부 통과"하는 경우를 계획에서 명시적으로 처리하는 분기를 마련해야 한다. (출처: pre-execution)
- 재시도, TTL 만료, 중복 큐잉 방지, 실패 시 상태 보존, 시간 기반 throttling 같은 비동기/큐 관련 핵심 동작을 구현할 때는 그 동작들을 직접 검증하는 전용 테스트가 존재하는지 확인하고, 없다면 테스트를 추가하거나 그 부재를 계획·보고에서 명시적으로 언급해야 한다. (출처: pre-execution)
- 변경 범위를 판단하기 전에 실제 git status를 확인해, 이번 작업과 무관하게 이미 modified 상태인 파일(다른 세션이나 사용자의 기존 변경)이 없는지 점검하고, 있다면 그 변경과 이번 diff를 명확히 분리해 관리해야 한다. (출처: pre-execution)
- 독립 비평/채점(예: 다른 CLI·에이전트를 통한 plan critique) 결과에 인증 실패, 파일 쓰기 권한 오류, dispatchFailed 같은 실행 오류가 기록되어 있으면 그 결과를 실질적인 비평으로 신뢰하지 말고, 환경 문제로 보고하고 재실행하거나 대체 수단을 확보해야 한다. (출처: pre-execution)
- 리뷰/검증 도구 호출 결과를 자동 수정(auto-fix) 파이프라인에 넣기 전에는, 그 결과 객체에 `dispatchFailed` 같은 "도구 실행 자체가 실패했다"는 플래그가 있는지 반드시 검사해야 한다. 이를 검사하지 않으면 실제 리뷰가 아닌 도구 장애 결과가 정상 리뷰 이슈로 취급되어 근거 없는 자동 수정이 실행될 수 있다. (출처: code-review)
- 구조화된 이벤트(JSON 등)를 파싱할 때는 필수 필드(예: request_id)만 있어도 정상 이벤트로 판정되도록 스키마 검증을 먼저 수행해야 한다. 정상 이벤트를 오류로 오분류한 뒤 전체 payload 텍스트에서 quota/usage 같은 키워드를 검색하면, 정상 완료 메시지에 그 단어가 우연히 포함된 경우 오탐 알림·불필요한 watch가 발생한다. (출처: code-review)
- 실패/에러 상황을 나타내는 envelope(응답 구조체)를 만들 때는, 그 envelope를 소비하는 스키마가 요구하는 필수 필드(예: checks)를 빠짐없이 채워야 한다. 필수 필드가 누락되면 실패 상태가 의도한 구조로 전달되지 않아 재시도·실패 처리 로직이 불안정해진다. (출처: code-review)
- 외부 CLI 도구를 서브프로세스로 호출해 그 출력에서 JSON을 파싱할 때는, 로그 파일·크래시 리포터 초기화 실패 등으로 인한 stderr 노이즈가 stdout과 섞이거나 도구가 유효 JSON을 전혀 출력하지 않을 수 있음을 전제해야 한다. JSON 파싱 실패 시에는 원본 출력을 그대로 노출/보존해 원인 분석이 가능하게 하고, 가능하면 실행 전에 도구의 로그 디렉토리 쓰기 권한 등 환경을 점검해야 한다. (출처: code-review)
- 외부 CLI 도구를 위한 샌드박스/허용 경로 목록을 구성할 때는, 문서화된 로그 경로만 허용할 것이 아니라 실제 실행 로그에서 "operation not permitted" 등으로 거부된 모든 경로(예: oauth-token, 세션/대화 기록, 캐시, 내부 상태 디렉터리 등)를 확인해 빠짐없이 허용 목록에 포함해야 한다. 그렇지 않으면 preflight 통과 후에도 실제 실행이 반복적으로 실패하고 재시도만 되풀이된다. (출처: code-review)
- 샌드박스/허용 경로 등 환경별로 달라질 수 있는 값을 설정할 때는 특정 사용자 홈 디렉터리 등을 하드코딩하지 말고, 실제로 참조되는 환경변수(예: HOME, AGY_LOG_ROOT)를 통해 동적으로 구성해야 한다. 하드코딩하면 환경변수 값과 실제 허용 경로가 불일치해 다른 환경이나 설정 변경 시 깨진다. (출처: code-review)
